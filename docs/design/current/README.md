## 项目目标与系统闭环

**2026-10-11 用户明确：最初理念是“让女仆活起来”，目标是类似环世界的故事生成器。居民有自己的想法、社交和活动，由此产生故事。玩家既是领地管理者，也是世界内的一名成员，可以通过管理事务、领主府女仆关系以及组建家庭参与故事。**

用户指出当前方向已偏向工作安排模拟器。下述生产经济闭环是此前方案，不能继续作为整个产品的首要目标；哪些机制保留、简化或调整尚待 Q39 讨论。已有具体规则不因本次方向复核自动撤销。关系、个人意愿与故事不再仅作为生产系统完成后的附加目标，但具体机制尚未定案。外部模组研究见 [Folkways 源码对照](../../references/folkways-analysis.md)。

### 此前生产经济方案（待目标复核）

2026-10-11 用户确认讨论顺序：先确定底层运行框架和生产循环的解决办法，再讨论如何在该框架上实现居民自主生活与故事。两阶段逐项议程集中维护在 [Q39 讨论计划](../../planning/OPEN_QUESTIONS.md)，具体架构尚待确认。

玩家以 Minecraft 世界内的领主身份建立营地，让有私产和生活需求的居民通过产业、工作、委托与交易维持城镇。真实采集与施工改变世界；不需要改动世界的设施允许后台运行。可观察的角色生活仍是目标，但不要求全城实体和区块常驻。

此前生产闭环为：剧本给初始居民与物资 → 玩家建立公共仓库、划地并放出资格证 → 招标选定出资居民 → 建筑工坊与生产产业建立 → 委托产生需求 → 管理员采购、工匠／劳动者生产 → 实际交付与结算 → 居民消费、产业备货与扩张。闭环尚未全部实现，首批资本和地皮几何仍有未决项；其在新目标下的范围与优先级待 Q39 复核。

## 模块边界

| 模块 | 现有职责／基础 | 新设计责任与边界 |
|---|---|---|
| FennecLib | 加权行为、UI 模板 | 保持基础能力通用；2026-10-11 已决定剔除 TLM 依赖，加权行为与 UI 模板由自身承载并脱离 Behavior 继承，独立算法核心见 I10 |
| MaidQuest（MQ） | 委托身份、认领、按单托管、找回、扩展接口 | 新增女仆财产挂件与对外接口、经济及劳动合约结算；不直接耦合 MMW 公共仓库实现 |
| MaidMoreWork（MMW） | 工程中心、采矿、伐木、工坊、图书馆 | 承载生产和产业工作能力，接入新的工时、财产、权限与物流规则 |
| MaidTown | 旧居民与篝火领地原型 | 暂缓代码开发；新剧本、招标、地皮、路网等跨系统功能的精确代码归属尚待设计拆分，不在此自行定模块 |

MQ 保持独立模组，不反向依赖 MMW／MaidTown。当前工作区事实见 [项目状态](../../planning/STATUS.md)，外部调用签名仍以各模块 API 文档及源码为准。

## 规则状态与优先级

- **已确认**：可以作为设计约束，但不等于已实现或已验收。
- **规则推导**：从已确认规则得到的衔接解释，原文明确标注；不冒充用户拍板。
- **待讨论**：产品选择、矛盾口径或未完整定义的异常分支，统一登记 Q 编号。
- **旧设计保留**：未被否定，但尚未与新体系对齐；长期章节保留来源，不默认开工。
- **代码事实**：仅描述本次静态核对结果，不能反过来修改目标设计。

优先级为用户最新明确确认 → 本套专题的确认规则（结合决策日志）→ 未被新规则覆盖的旧技术约束。归档文件只是证据，不能凭标题里的“已确认”“最终”“待实现”覆盖当前规格。发现专题与新用户确认冲突时，更新专题和 Q／C／I 对应条目。

## 共同开发约束

- 同一份实物、货币和生产作业不能因重试、加载切换或多入口重复结算；交割失败应保留可定位的实际货物。具体跨模组事务机制仍属 Q27 技术细化。
- 物品所有者、保管位置、执行者是不同概念。中心保存物资不等于中心是独立经济所有者。
- 区块卸载、维度卸载、死亡、玩家收起、停服、跳夜分别处理；没有实体不能直接证明死亡或离职。
- 无配置确认的阈值不自行写死；已有 1000 tick 冷却、3000 tick 外部中断等规则不重复询问。
- 不把旧报告中的编译成功当成当前源码构建结果，也不把构建当游戏验收。
