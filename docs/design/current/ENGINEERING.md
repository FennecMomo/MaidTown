## 通用行动权重判断（2026-10-11 目标设计，尚未实现）

用户确认所有居民行动统一走权重体系，公共接口用于决策节点的行动选择，不另设拒绝阈值或拒绝概率关卡。需求、状态与经历改变行动权重；按权重概率选择的方向已定；具体概率公式、因素合成、资格检查边界、接口签名及模块归属尚未确定。

2026-10-11 Q39.1.g 已确认选择方向：按权重形成概率，权重越高越容易选中，不采用最高权重必选；较低权重的候选行动也有机会。居民饥饿时仍可能选择出去兜风，这种不可完全预测的取舍是用户希望的生活感，不能以总选最迫切需求替代。具体概率映射、权重取值范围及零／负值处理仍未确定，不擅自规定为线性归一化。随机选择发生在已确认的决策节点，不因此每 tick 重新抽取。

上级派工同样是带权重的行动。用户澄清因果：生病产生 debuff，debuff 影响工作效率，上级根据所见工作效率调整派给该员工的权重，不直接以“生病”扣派工权重。居民自身则因生病提高就医行动权重，不直接扣自己的工作行动权重。雇员没有拒收上级派发任务的权力，但工作归属不强制决定当前行动；需要工作对执行该工作有正面权重影响。任务归属与行动执行需区分，具体数据结构待 Q39.2；Q39.1.i 已确认：上级派任务时根据员工当时的工作效率决定，允许结果有误差或受临时因素影响；当前不另设观察／工作记录的信息获取机制，也不据此要求额外随机误差算法。派发后的延期和改派规则仍待讨论。

Q39.1.c 已确认采用“基础权重＋因素修正”的结构，但因素必须按实际因果作用于对应行动，不能让疾病在工作权重上重复产生直接扣分。这里的结构确认不锁定加法／乘法等数值公式。就医权重提高后会影响行动选择，效率变化会影响工作完成速度，从而间接影响任务；具体概率映射与效率计算仍待细化。

开始工作或中断后准备继续时判断；执行过程中不持续重评意愿，事件仍可打断。暂不继续则原工作搁置，先派工后生病造成延期是允许的结果。相邻决策节点如何避免重复调用、搁置后何时再判断、资源释放及改派尚待讨论。通用接取节点用于需要主动接取的行动，不得据此给雇员派工重新加一道拒收检查。

详见 [委托产业](QUESTS_AND_INDUSTRIES.md) 与 [居民生活](RESIDENTS.md)。以上不等于现有加权行为库已完整实现这些规则。

### 重判、打断与进度恢复（2026-10-11 已确认方向）

- 用户同意采用监听触发的接口方向：普通需求或重要状态变化请求重判，在可暂停节点选择行动；无法继续执行的事件强制打断，恢复能力后再判断。不因每次数值微变持续重选；合并重复请求的方向保留，具体监听条件、频率和性能预算未定。
- 请求重判不等于先销毁或重建当前行动。重判仍选择当前行动时继续原实例及进度，避免“吃饭→收到工作→仍选吃饭→从头吃”的循环。
- 实际被打断或切换走的行动必须保存可恢复进度；以后继续同一行动时从保存位置恢复。此规则覆盖生活行动和生产行动，不只保存整份工作订单的完成数量。
- 用户举例：吃饭被打断后仍应保留已进行的进度，继续吃时不能从头开始。不得通过新建同类行动清掉该进度。
- 待细化：进度最小内容、暂停时持有物与资源占用、恢复时目标或物品失效的处理、完成与消耗如何避免重复。具体恢复校验规则不是本次已确认方案，记入 Q39.1.k，并接 Q39.2／Q39.4／Q39.6／Q27。

### 紧急行为（2026-10-11 已确认）

- 前台实体纯执行，不自行改变意图，也不自行处理意外；它兼任观测者，把观测到的特征点事件（例如着火、受到攻击）上报给后台。
- 后台收到上报后启用紧急决策：单独定义一组“紧急行为”，这些行为**不作为权重选项**，触发时立即插入执行，既不参与按权重抽取，也不等下一次决策节点。
- 与既有机制的分工：无法继续执行的事件仍走“强制打断＋重判”这条既有通道；紧急行为是更窄、更快的一条独立通道，只处理触发即须立刻反应的少数情况。普通监听请求不因此改成紧急插入。
- 2026-10-11 成员范围已确认：①生存类——着火、溺水／耗氧、岩浆与仙人掌等持续伤害源、受到攻击、坠落自救；②边沿型“行动继续不下去”——工具损坏、设施被拆、材料被取走这类一次性事件。二者触发即插入，不经权重抽取。
- 不进紧急通道：容器满、目标格被占、路不通等**持续状态**（电平型）——它们在状态未变时会被反复观测到，若按触发即插入会形成“报告→插入→再失败→再报告”的循环；这类仍走既有的失败重试、寻路熔断上报与路网复核。判据：边沿触发（事情发生的那一刻）进，电平触发（状态持续存在）不进。
- 插入语义已确认（2026-10-11）：紧急行为结束后统一检查原行动是否仍可继续——可继续则按 Q39.1.k 保存的进度恢复（不从头开始），不可继续则走既有的“无法继续执行的事件强制打断”重新决策；不做“一律先尝试恢复”的空转，也不一律放弃原行动。
- 优先级已确认（2026-10-11）：采用固定优先级表并按紧迫度允许抢占——溺水／耗氧 > 着火 > 岩浆与持续伤害源 > 受到攻击 > 坠落自救 > 工具损坏／设施被拆／材料被取走；同级按触发先后，处理中遇更高优先级则抢占，被抢占者条件仍在时重新触发；同一条紧急行为处理中不重复插入。
- 待定（Q39.18）：是否允许玩家配置（优先级顺序、成员开关等）、生存类清单的继续增补。

## MQ 委托数据与交互

当前代码使用每维度 `QuestBoardData` 保存订单、板坐标、每单托管及找回条目，方块实体是交互入口。发布者／执行者用 `QuestActor` 身份判权；女仆 Attachment 存当前委托执行缓存。客户端通过查询／快照／观看会话同步，不再把板级共用 54 格容器作为交付托管。

玩家与女仆／模组调用汇聚到服务入口；当前仅女仆接单。委托模式是全局配置，不是旧计划中的每女仆面板按钮。接单资格和权重是两层：资格筛掉不能供货者，权重在可选者中选择。

现有找回和死亡处置回调、拆板 UI、直接挖板拦截可作为基础。**当前取消／死亡返货按交付者、收起立即重开的业务规则与最新设计不同**，不能整体照搬旧实施文档。公开方法见 [MQ API](../../../maidquest/docs/API.md)；新财产 API 尚不存在，不能虚构签名。

## MMW 中心与产业基础

- `ProjectCenterInstance` 基类已包含仓库与困难表，`ProjectCenterData` 负责持久化，`ProjectCenterManager` 管理实例。矿井、工坊、林场共用框架。
- 工坊持有制作订单、预留材料、配方及备货目标，管理员与工匠分工；图书馆提供配方知识，当前实现仍以工作台制作链为基础。
- 林场有管理员、成员、工具借还、供货与界面。伐木回落到个人搜索／工程搜索，不复活 SPBlock 方案。
- 工坊／林场 54 格分页、矿井 45 条目分页及基础仓库已有代码，但产业只读权限、公共仓库单位容量、经济物流不是这些菜单自然附带的能力。
- 前后台工坊制作已有两个入口，须改为共同工时规则；现有中心全局 tick 不等于完整居民后台模拟。

公开扩展契约见 [MMW API](../../../maidmorework/docs/API.md)，图书馆／工坊细节与历史审查见 [文档台账](../../archive/DOCUMENT_REGISTER.md)。旧开发交接中的命令和开发授权仅对应当时任务。

## 矿井：保留的技术约束

来源：[矿井重构全文](../../archive/2026-10-07/maidmorework/docs/design/MINE_REDESIGN.md) 与 [螺旋坐标参考](../../../maidmorework/docs/design/MINE_SPIRAL_ALGORITHM.md)。旧文中同日多次修订已分层，下面不把相互矛盾的段落同时当规格。

| 主题 | 归并后的技术内容 |
|---|---|
| 几何 | 螺旋规划与中心作业范围分开；螺旋边长奇数、至少 7，框选非正方形按长边居中取正方形；深度受中心范围底面限制。原螺旋公式作为现有算法保留，本轮不改 |
| 派工 | 一层竖井工程，多人逐坐标执行；横向矿道独立工程，旧确认容量 3；请求时先续手头工程，再选可参与工程 |
| 工序 | DESTROY／FILL／REPLACE／SETLIGHT 等按实际方块派发；保留→挖掘→补充→光源；后续增加层控制方块和地面火把等，不能只凭“四型”断言当前枚举仅四种 |
| 保留位 | 空气补洞；正确实体保留；最新收窄为矿物换垫脚回收，不能按旧表把所有石头实体一概替换 |
| 工具 | 推荐工具要求类型匹配且能正确掉落；自身→仓库；非必须正确工具时可空手；否则寻找必要工具；无可用工具进入困难表。派发侧／执行侧职责旧文有相反说明，见 Q29，需以目标契约核对源码 |
| 挖掘 | 真实破坏进度及工具耐久，工具速度与硬度参与；不保留旧 TODO 的“完全缺少工具等级与效率”的笼统判断 |
| 流体 | 水源清除、生成流体瓶、原位置塞子；非保留位临时塞子随后维护移除；无产物工序不产生矿工工分 |
| 光源 | 后期确认只认火把；旧 B2 的任意发光物品不再作为当前支持清单，挂顶灯笼另列工作项 |
| 复核 | 坐标池清空且无人作业后等待 40 tick 复核；维护按封存类型检查，跳过未加载位置；不是每 tick 全矿扫描 |
| 层控制器 | 关联矿井 UUID、按平台生成；旧确认不消耗物品，随矿井清理；该特殊例外不能推广为普通施工材料凭空产生 |
| 仓库 | 继承中心缓存、工具取用和产物入库；旧 27 格容量限制退出；矿井仍为 45 条目分页，但控制行已改真正按钮／页码，工坊和林场另用 54 格分页 |

代码已含 `MineTunnelProject`、`MineInstance.buildTunnelPlan` 的纵道与横向分支，旧“尚无鱼骨矿道，必须新增 FishboneMinePlanner”不能原样作为待开发任务。是否满足全部原几何需求仍需核对，未做游戏验收。

旧文对挖尽后留员／释放、维护持续／停止有多次同日修订；当前代码在竖井挖尽且矿道全完后停止部分封存巡检。记录为实现事实与 Q29 衔接项，不擅自重新宣布其中一种为用户的新决定。

跟随采矿的保留方案：沿玩家路径搜露天矿，标签识别、至少一面邻空气、工具可采；跳过已占用坐标，超距归队；背包满默认停止，可配置，不接矿井仓库存货。参数默认值与是否已经完整接入见 I09，不能与 Home 模式混用。
