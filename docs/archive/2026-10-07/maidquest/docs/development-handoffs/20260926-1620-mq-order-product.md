# MaidQuest：可选物品订单与工坊供货接口交接

项目目录：/mnt/d/ModProduce/MaidTown/maidquest

## 目标与边界

本次只实现 MQ 一侧。玩家在委托板发布制作订单时必须能选具体物品与数量；服务器保存并校验物品，不能在 CraftingQuest.Type.create 中写死木镐。保留现有 IQuestType 等第三方扩展 API，保持 MQ 单独运行可加载。MMW 下一阶段负责图书馆、制作配方、工坊和林场；MQ 要提供清晰、稳定的订单与材料接口，不把 MMW 的生产逻辑移入 MQ。不要改 MaidTown、FennecLib 或其他仓库。

委托模式按钮当前在 CommissionModeClient 固定放于 GUI 右侧，会挡住 TLM 其他控件。用 TLM MaidContainerGuiEvent.Init 取得 event.getGui()，再检查 GUI 的 getExclusionArea()（返回 List<Rect2i>）和 getEventAddButtons()（返回 Map<String, AbstractWidget>）来确定实际界面布局；这两个方法不在 Init 事件自身，为按钮找安全位置；不同分辨率、任务列表展开时均不遮挡现有按钮。按钮仍由服务端持久化和回包刷新。

## 制作物品选择和服务器校验

- 委托板制作类型的详情增加物品选择控件，显示物品图标、名称、模组来源和搜索；保留数量输入。候选为服务端当前配方管理器中的真实工作台配方产物，支持其他已加载模组的配方。无需图书馆已录入才可发布，未录入正是后续缺配方请求的触发条件。不要把所有注册物品都当可制作物品。
- 对多人游戏，服务端向打开委托板的玩家发送候选产物 ID；客户端不得以本地配方书解锁情况作为完整列表。列表/搜索做有界同步，避免一次性发送过大包。发布按钮在未选择物品时不可用，列表重载与界面关闭后不保留错误选项。
- QuestPublishPayload 对制作订单增加所选物品 ID；其他委托类型可不传。服务端验证方块距离、类型权限、数量范围、物品注册与当前工作台配方产物匹配，拒绝非法载荷并给玩家明确反馈。显示订单时同时显示实际物品与数量，避免多个同为“制造”的订单无法区分。
- CraftingQuest 已持久化 item Identifier，继续沿用；Type.create 不再强制写入 WOODEN_PICKAXE。为 IQuestType 增加向后兼容的产品参数入口，原有扩展实现和 API 调用保持可编译。已有木镐测试订单存档仍可读。

## 通用材料订单及认领关系

- 现有 MaterialQuest 被写成固定原木需求，扩充为带明确物品条件的材料订单：精确物品或所选配方 Ingredient 接受的有限候选集合。序列化条件、父订单/备货需求来源、发布者 UUID、收货者 UUID、数量及既有订单 ID；兼容读取旧原木单，默认旧条件为可制作木板的原木。对同一需求的未完成子单做去重；完成且仍有托管货物时继续保留领取权。
- 原木仍由木匠本人发布；MMW 后续改为林场管理员接取原木单，故 MQ 的材料类型硬资格从“伐木工种”改为“经 MMW 注册的供货资格”，MQ 不直接依赖 MMW 类。通用材料单的交付、部分交付、托管、领取、取消、重载必须按订单 ID 与物品条件核对，禁止串单与重复提取。
- 制作订单资格只检查制作工种与有效工坊，不检查女仆是否已经会该配方；不会做也允许认领，交由 MMW 在图书馆学习或等待。为 MMW 提供查询当前订单、发布去重的材料子单、按身份领取完成材料、标记等待原因/恢复的服务端入口。未知配方期间订单保持认领，不自动放弃。
- MQ 对外暴露材料单服务端接口的最小数据：目标条件、剩余量、父单 ID、收货者、托管量和状态。不要强迫下一阶段从 UI 文本解析需求。必要时提供事件/回调让 MMW 判断管理员能否接该材料订单。未有供应方的其他原料需求保持可见等待；玩家也可直接把材料放入工坊，MMW 会重新计算缺口。

## 第二轮设计修订（主人 2026-09-26 补充）

制作订单归属 MMW 工程中心，工程中心以稳定 UUID 持有订单对应的制作工程、配方知识和材料预留；工匠女仆只是被分配的执行人员。任一工程中心都要绑定一名管理女仆，管理女仆代表中心发布缺料单、领取完成的材料并入中心仓库。管理女仆更换或工匠重派后，既有材料单的来源、货物和领取权必须继续归同一个中心，不得困在旧女仆 UUID。MQ 只提供通用来源/受益中心与领取身份的服务端接口，不反向依赖 MMW 类；兼容旧材料单存档。制作单仍由委托板持有面向玩家的订单记录，MMW 中心持有执行工程与预留物资。

上一轮独立审查需要修复并复审的事项：

1. `QuestService.materialFor` / `requestMaterial` 复用子单时未检查收货身份；`withdrawMaterial` 又只许旧 requester UUID 领取。增加安全的管理女仆交接/中心受益身份机制，确保换人后同一中心可取回已托管材料，且别的中心不可领取。不要只按工匠 UUID 绑定。
2. `MaterialQuest.Type.canClaim` 无注册供货资格时的伐木回退仍须检查订单条件；非原木材料不可被伐木工认领。
3. `materialInfo` 的完成单剩余量要保持 0，不能在领取托管货物后重新变成原始数量。
4. `CraftingCatalog` 配方重载后须及时失效/重算缓存，服务器不能暂时接受已无效产物。
5. 委托模式按钮在 TLM 任务列表动态展开后仍须重新检查排除区域；静态审查无法代替用户的画面确认。
6. `MaterialCondition.of` 不得悄悄截断有效候选，也不得产生无法由 CODEC 保存的空条件；服务端应明确拒绝无效或超界的请求。

本轮 MQ 编译命令仍为 `./gradlew jar`，只做编译打包，不运行游戏、测试、lint、浏览器或截图。最终 MQ JAR 位于 `build/libs/maidquest-0.0.1.jar`，MMW 构建依赖该 JAR。桌面联调 BAT 实际从 MQ `build/classes/java/main` 与 `build/resources/main` 加载开发源输出，MQ JAR 不应再复制到 `run-shared/mods` 造成重复加载。
