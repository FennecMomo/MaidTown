## 1. 设计支柱

| 支柱 | 说明 | 一句话验证标准 |
|------|------|---------------|
| **你是他们中的一员** | 玩家以第一人称存在，不是上帝/摄像头。你和居民一起挖矿、一起战斗、一起吃饭。 | 玩家关闭 UI 后仍然可以"直接看到"所有发生的事情。 |
| **每个名字都有重量** | 居民不是工具人。他们有名字、特质、记忆、关系、私有财产。失去一个人应该让玩家心痛。 | 当有人说"我家的老王死了"而不是"我死了一个矿工"。 |
| **活着本身就是挑战** | 资源稀缺、环境危险、居民会饿会累会崩溃。舒适是奢侈品。 | 第一夜来临前，玩家必须做出有意义的取舍。 |
| **从零建造，眼见为实** | 所有建设发生在 MC 世界中，玩家亲手（或指挥居民）放置每一个方块。 | 没有抽象的建筑菜单——一切都在世界里。 |

## 2. 核心游戏循环

### 2.1 时刻循环（30 秒内）

```
玩家观察环境 → 判断优先级 → 给居民下达指令 / 自己动手 → 看到结果反馈
```

### 2.2 昼夜循环（20 分钟）

```
白天：采集资源、建造扩建、探索周边
黄昏：盘点库存、分配任务、加固防御
夜晚：居民休息恢复、玩家守夜或睡觉、敌人可能来袭
```

### 2.3 长线循环（数小时–数天）

```
领地扩张 → 吸引更多居民加入 → 需求压力增大 → 需要更高效的产出
→ 探索更远/更危险区域获取稀有资源 → 触发事件/故事
→ 居民之间产生羁绊/冲突 → 领地有了自己的"历史"
```

### 2.4 日节律与时间系统

> 核心设计：居民 6:00–18:00 工作，18:00–次日6:00 自由活动。工作时间 tick 运行（玩家可见），自由时间数据化结算（不运行 AI）。

#### 时间轴

```
MC 时间   6:00           18:00                   次日 6:00
MC tick   0              12000                   24000→0
         ├──── 工作时间 ────┤──── 自由时间 ─────────┤
         │                  │                        │
         │ 正常 tick 运行    │  玩家在线 → tick 正常    │
         │ 玩家能看见        │  玩家睡觉 → 批量结算    │
         │ 产生物资          │  不产生物资             │
         └──────────────────┴────────────────────────┘
```

#### 工作时间（6:00–18:00，约 10 分钟现实）

- 居民按职业/任务进行生产活动（采集、建造、加工等）
- AI 正常每 tick 运行
- 玩家可下达指令、观察、交互

#### 自由时间（18:00–次日 6:00）

- 居民不进行生产活动
- 进行娱乐/恢复性活动：吃饭、睡觉、聊天、闲逛、看书、锻炼等
- **两种运行模式**：

| 模式 | 触发条件 | 行为 |
|------|---------|------|
| **实时模式** | 玩家在线（熬夜/通宵） | 居民在领地内自由活动，tick 正常运行，玩家可观察 |
| **批量结算模式** | 玩家入睡（跳过黑夜） | 遍历所有居民 → 统一 apply 数值结果 → 返回简报 |

#### 自由时间活动 & 结算效果

| 活动 | 前提条件 | 结算效果 |
|------|---------|---------|
| 吃饭 | 玩家箱子/居民私有食物 | 饥饿值 ↑ |
| 睡觉 | 有床 | 休息值 ↑ 满 |
| 聊天 | 附近有其他居民 | 好感度 ±（可能吵架也可能交好） |
| 闲逛 | 无 | 可能触发随机事件（发现/意外） |
| 看书 | 有书架 | 心情 ↑；[PLACEHOLDER] 未来可挂钩技能 |
| 锻炼 | 开放空间 | 体质微调 [PLACEHOLDER] |

#### 批量结算流程

```
玩家入睡 → 夜晚 tick 直接跳到 0
    → 遍历所有居民：
        · 扣除跳过时长的饥饿被动消耗
        · 根据可用资源 apply 自由活动效果
        · 生成随机社交事件
    → 玩家醒来 → 收到简报：
        "昨晚老王和老李吵了一架。小芳读完了一本书。"
    → 居民从各自床边正常开始新一天
```

#### 设计意图

- **不模拟 AI，只结算数据**：跳过时间时不运行复杂的行为树，只更新状态值。实现成本极低。
- **为守夜系统留空间**：以后引入守夜/夜班时，只需在自由时间段加一个"夜班工作"活动类型，结算逻辑不变。
- **玩家自然的作息约束**：早睡 → 居民休息充足；熬夜 → 居民自由活动时间短，可能休息不足（引入疲劳系统后体现）。

### 2.5 世界加载与模拟边界（2026-09-28 修订草案）

本节补上原设计遗漏的加载生命周期。**区块卸载、单个维度卸载、服务器停机和玩家睡觉跳时分别处理**。服务器仍在运行时，区块卸载仍可维护世界存档中的订单、中心、预留和找回记录；它不证明女仆、工作台或目标方块仍可交互。单个维度卸载暂停该维度的推进，不影响其他维度。服务器停机不推进工作，也不按现实时间补产出。睡觉跳时只按 §2.4 结算已定义的自由活动，不补做采集、制作和物流。

MQ 与 MMW 的当前 TLM 女仆尚未接入本 GDD 的 6:00–18:00 作息；因此上面的昼夜时间表是 MaidTown 后续目标，不应声称现有工坊已经遵守。将来接入时，同一套工作时段必须同时约束已加载实体行为和可能的抽象加工，避免一边休息一边后台生产。

订单、工程和库存的持久记录与实体现场操作分开：区块卸载保留身份和物资归属；重新加载后核对方块、女仆及绑定。死亡、收起、换岗、真实拆除走明确事件，不能用“当前找不到实体”替代。具体分层、工坊卸载制作的待决选择与验收场景见 [MQ × MMW 加载边界设计](LOADING_AND_SIMULATION.md)。

## 4. 居民活人感维度

> 设计目标：让每个居民不只是"会动的状态条"，而是有血有肉的存在。

| 分层 | 特征 | 成本 | 说明 |
|------|------|------|------|
| **立刻感受到** | 名字+口头禅+小动作+心情+住处+财产 | 低 | 玩家第一眼就能感知的差异化 |
| **相处一阵感受到** | 习惯路径、日常节律、关系变化、记忆 | 中 | 需要观察一段时间才能发现 |
| **深交后才发现** | 信念、执念、受伤史、单向感情、忠诚演变 | 高 | 需要特定事件触发或长期积累 |

### 维度清单

| 维度 | 内容 |
|------|------|
| **空间** | 住处、工作台、习惯路径、归属感（不进别人箱子） |
| **时间** | 日常节律（几点起床/吃饭/休息）、过去记忆、未来期待 |
| **社交** | 关系深浅分级、单向感情、社交需求差异、冲突记忆 |
| **认知** | 世界观/信念、忠诚度演变、迷信/执念 |
| **物质** | 财产所有权、物品偏好、收藏癖 |
| **生理** | 体质差异（耐饿/怕冷/跑速）、受伤史、年老化 |
| **行为** | 小动作（踱步/擦汗）、口头禅、道德边界 |

## 5. 领土与地契系统

### 5.1 双层结构

```
┌─────────────── 领地 (Settlement) ───────────────┐
│  中心：篝火（最初阶段的领主办公点）                  │
│  范围：以篝火为中心 101×101（暂定），无限高         │
│  属性：公有制——玩家有管理权                          │
│                                                   │
│   ┌── 地契 A（居民甲）──┐   ┌── 地契 B（居民乙）──┐ │
│   │ 形状：严格长方体       │   │ ...                 │ │
│   │ 范围：玩家手动框选     │   │                     │ │
│   │ 属性：甲私有           │   │                     │ │
│   │ · 甲有该区域内所有     │   │                     │ │
│   │   方块的归属权         │   │                     │ │
│   │ · 玩家未经许可拿/拆   │   │                     │ │
│   │   → 扣声望           │   │                     │ │
│   └──────────────────────┘   └─────────────────────┘ │
│                                                   │
│   └── 公有区域（道路、广场、未分配地皮） ──────────┘ │
└───────────────────────────────────────────────────┘
```

### 5.2 地契规则

| 规则 | 决策 |
|------|------|
| **形状** | 严格长方体（多块拼接实现复杂布局，简化寻路和建造系统） |
| **不可重叠** | 玩家框选时已售区域变色显示 |
| **定价公式（V1）** | 空间体积 + 内部有效方块价值（不做楼层次优等复杂变量） |
| **领地外区域** | 玩家可随意建造；居民不限制工作范围（行为有目的性：矿工挖矿、伐木工砍树、渔夫找河流，不会跑太远） |

### 5.3 地契获取方式

| 方式 | 流程 |
|------|------|
| **贡献点兑换** | 居民攒够贡献点 → 向玩家提出购地申请（可指定长宽高限制，防止有人卖"一条直线"）→ 系统自动计算价格 → 玩家手动框选区域 → 确认 |
| **继承** | 原主死亡 → 按继承权分配 → 无人继承 → 充公 |
| **逃离充公** | 居民逃离 → 先变卖资产 → 卖不出去 → 充公 |

### 5.4 玩家与居民领地的交互规则

#### 5.4.1 玩家私自进入居民领地操作

| 行为 | 后果 |
|------|------|
| 破坏方块、拿走物品 | 扣声望 + 警告提示 |
| 私自放置方块 | 扣声望 + 放置物归属权自动变为该居民 |

#### 5.4.2 公共设施改造流程

```
玩家发起改造请求（沟通选项）
    → 居民同意
    → 进入施工模式（限时）
    → 时间到期或玩家主动完成
    → 系统更新所有权、检查方块内容变化
    → 居民少东西 → 向玩家索赔 → 不赔 → 扣声望
```

#### 5.4.3 拆迁 / 收购居民领地

```
玩家发起收购（居民的沟通选项）
    → 玩家支付赔偿
    → 如果拆迁的是居民的住宅：
        → 玩家必须提供新的住宅（已有地契或新建）
        → 并补差价（新住宅价值 < 旧住宅价值时）
```

## 6. 功能区系统

> 不从几何推语义，从锚点推语义。

### 核心思路

| 原则 | 说明 |
|------|------|
| **不扫描封闭空间** | 不管墙壁，不管房间是否完整，不依赖几何计算 |
| **按功能方块判定** | 一个炉子 → 周围就是厨房；一张床 → 周围就是卧室 |
| **影响半径** | 每个功能方块覆盖周边 N 格 |
| **性能友好** | O(N_furniture)，不是 O(N_blocks) |

### 功能方块映射（示例）

| 方块 | 功能区类型 | 影响半径（[PLACEHOLDER]） |
|------|-----------|--------------------------|
| 床 | 卧室 | 2 格 |
| 熔炉 | 厨房 | 3 格 |
| 工作台 | 作坊 | 4 格 |
| 箱子 | 仓库 | 3 格 |

### 功能区与所有权

```
功能方块的所有者 = 功能区的主人
→ "这个工作台是 B 的" → "这里是 B 的工坊"
→ 居民通过重复使用→事实占有，无需显式分配
→ 床的所有权绑定地契
```

## 7. 物品所有权系统

> 整个经济系统只需要一个核心数据模型：物品/方块 + 所有者 + 位置 = 经济、空间、所有权的统一坐标系。

### 物品所有权标签

每个物品堆在 NBT/数据组件中携带 `Owner` 字段：

```
物品堆 = { item: "oak_log", count: 16, owner: "A" }
```

| 动作 | 所有权变化 |
|------|-----------|
| 采集（野生资源） | 无主 → 采集者 |
| 交易 | A → B |
| 加工 | 原料(消失) → 产物(生产者) |
| 放置为方块 | 物品所有者 → 方块所有者（若在公有区域）/ 归入地契主人（若在私有领地） |

### 物品所有权与空间归属的联动

```
A 砍树 → 原木(A)
A 交易给 B → 原木(B)
B 在工坊加工 → 木板(B)、床(B)
B 卖床给 D → 床(D)
D 放置床 → D 的卧室（床所在半径内 = D 的卧室区）

路径切换：
  ┌─ 情况 1：D 把床放在空地 → D 拥有这间卧室
  ├─ 情况 2：D 把床放在自己搭的小屋 → D 拥有小屋+卧室
  └─ 情况 3：D 把床放在从 E 买的房子 → D 拥有卧室，房屋归 D
```

## 8. 贡献点经济系统

### 8.1 经济模型

```
玩家采集/狩猎/制造
    → 获得物资（食物、装备、建材）存入私人箱子
    → 玩家用物资悬赏任务
    → 居民完成任务
    → 居民获得贡献点 + 实物奖励
    → 居民用贡献点向玩家购买物资、土地、装备
    → 贡献点回流玩家 → 继续悬赏任务 / 发工资
```

贡献点本质是**记账单位**，对应玩家箱子里的实物。不是独立货币——不会通胀。

### 8.2 工资系统（后续）

后期卫队、专职居民需要定期发工资：

```
卫队规模 ↑ → 工资总支出 ↑ → 玩家需更多物资交付 → 需要更多生产居民 → 经济压力自然约束扩张
```

养兵需要后勤——断饷的后果 [PLACEHOLDER] 待后续讨论（叛乱？士气低落？逃离？）。

### 8.3 贡献点用途（居民视角）

| 用途 | 说明 |
|------|------|
| 购买食物 | 基础生存 |
| 购买装备/工具 | 提升工作效率 |
| 购买地契 | 获得私有空间 |
| 购买房屋 | 从建筑工/其他居民处购买 |

## 9. 声望系统

### 9.1 两种声望

| 声望类型 | 影响 | 说明 |
|----------|------|------|
| **领地声望** | 影响居民整体满意度、新居民加入意愿 | 公共治理水平的反映 |
| **个人声望** | 影响特定居民对玩家的态度 | A 对玩家的声望低 ≠ B 对玩家的声望低 |

### 9.2 声望增减事件

| 事件 | 声望变化 |
|------|---------|
| 玩家未经许可进入居民私有领地破坏/拿取 | 大幅下降 |
| 玩家改造公共设施→居民同意→过程中居民财产受损→不赔 | 大幅下降 |
| 玩家完成居民请求 | 上升 |
| 居民长时间饥饿 | 缓慢下降 |
| 居民死亡（非战斗原因） | 领地声望下降 |

### 9.3 逃离机制

```
声望降至逃离阈值 → 居民变卖资产（卖给其他居民/玩家）
    → 卖出 → 带上货币离开
    → 卖不出 → 资产充公 → 离开
```

## 10. 指挥与征召系统

> 设计原则：居民默认自治——上班干活、下班回家。玩家不能当"随身挂件"一样拖走所有人。

### 10.1 状态模型

```
驻守状态（默认）
    → 居民在领地内自主工作
    → 工作时间：按职业/任务干活
    → 自由时间：回家、吃饭、社交
    → 完全自驱

征召状态（指挥棒切换）
    → 居民放下当前事务，跟随玩家
    → 离开领地期间不受工作时间约束
    → 玩家解散后恢复驻守
```

### 10.2 征召响应规则

| 居民角色 | 能否征召 | 行为 |
|---------|---------|------|
| **卫兵**（领工资的专职战士） | ✅ 随时响应 | 放下一切立刻跟随，无条件服从 |
| **普通居民（无卫兵时）** | ✅ 响应 | 领地没有卫兵时，最近的普通居民会跟随保护玩家 |
| **普通居民（有卫兵时）** | ❌ 拒绝 | "我还有事要忙"——手头有工作任务时不会中断 |
| **普通居民（空闲时）** | ✅ 可能响应 | 自由时间/无任务时可以被征召 |

### 10.3 指挥棒交互

```
玩家手持指挥棒
    ├── 右键地面 → 征召最近的可用居民到该点（优先卫兵）
    ├── 右键方块（树/矿石）→ 指派最近可用居民采集
    ├── 右键居民 → 切换驻守/征召状态，或打开状态面板
    └── Shift+右键居民 → 解散回驻守
```

### 10.4 设计意图

- **卫兵的价值**：唯一能无条件跟随的角色，让"发工资养卫队"有直接的游戏性回报
- **普通居民的自治感**：拒绝跟随时说"还有事要忙"——这是活人感的一部分，让玩家感受到居民有自己的生活
- **安全兜底**：没有卫兵时至少有一个居民会保护玩家，避免玩家落单时完全无力

### 12.3 关系系统

#### 数据模型

**单向好感度**——A 对 B 的好感和 B 对 A 的好感各自独立存储：

```
关系矩阵：
         A     B     C
    A    —    +80   -20
    B   +30    —    +50
    C   +10   -40    —
```

- A 喜欢 B（+80），但 B 对 A 一般（+30）——A 跟 B 聊天时 A 心情上升，B 无所谓
- B 讨厌 C（-40），但 C 对 B 还行（+10）——B 跟 C 聊天时 B 心情下降，C 正常

| 冷淡 | -20~-1 | 不太想搭理 |
| 讨厌 | -50~-21 | 会吵架、心情负面影响 |
| 仇人 | -100~-51 | 见面心情暴跌、可能主动找茬 |

### 12.5 故事 & 事件系统

> 轻量设计：提供可扩展的事件 API 框架，V1 仅内置少量核心事件。其余留给模组生态扩展。

#### 事件 API 框架

```
EventTrigger（触发条件）
    → 检查前置条件（领地状态、居民状况、时间等）
    → EventAction（事件行为）
    → EventOutcome（结果：数值变化 + 消息通知）
```

支持两类触发：

| 触发类型 | 说明 | 示例 |
|---------|------|------|
| **条件触发** | 满足条件时自动触发 | 居民连续吃同一种食物三天 → 抱怨事件 |
| **定时随机** | 按时间间隔从事件池按权重抽取 | 每 N 天从随机池抽一个事件 |

#### V1 内置事件池

| 事件 | 类型 | 效果 |
|------|------|------|
| 袭击 | 定时随机 | 一波敌对生物进攻领地，卫兵/居民自动迎战 |
| 商队 | 定时随机 | 临时商队到访，可交易稀有物品 |
| 流浪者加入 | 定时随机/条件 | 新居民请求加入领地（需玩家同意） |
| 居民抱怨 | 条件触发 | 基于需求/心情/关系系统中的不满条件触发 |

> ⚠️ **闲聊、吵架、踱步、发呆等小行为不属于事件系统**——这些是居民个体 AI 的行为层（见 2.4 自由时间活动），不是宏观叙事事件。事件系统只处理影响整个领地或多个居民的大型事件。

#### 设计意图

- V1 只需跑通事件管道，不求事件数量
- 事件池可扩展——后续版本或第三方模组可注册新事件
- 条件触发保障合理性，定时随机制造意外

### 12.6 战斗系统

#### 战斗角色

| 角色 | 定义 | 日常行为 |
|------|------|---------|
| **卫兵** | 领工资的专职战士 | 领地内随机巡逻，遇敌自动攻击 |
| **民兵** | 有战斗技能的普通居民 | 正常工作；袭击时回家取武器→切换卫兵AI |
| **普通居民** | 无战斗能力的居民 | 袭击时躲藏，极近距离遇敌时自卫逃跑 |

#### 两种战斗模式

##### 日常巡逻

```
卫兵在领地内随机巡逻
    → 视野范围内发现敌对生物
    → 自动前往攻击
    → 战斗结束 → 恢复巡逻
```

##### 袭击响应

```
袭击事件触发 / 卫兵或哨塔发现袭击敌人
    → 敲响警钟（全领地通知）
    → 普通居民：寻找最近的安全位置躲藏
    → 民兵：
        → 回自己家取武器
        → 切换到卫兵 AI
    → 卫兵：
        → 视野范围临时 ×2
        → 前往发现敌人的位置
    → 战斗结束 → 解除警报
        → 民兵归还武器，恢复日常工作
        → 卫兵恢复巡逻
        → 居民从躲藏处出来
```

### 12.7 建筑系统

> 核心设计：建筑 = 空壳 + 内部自主布置。不使用固定模板——由零件规则引擎按地块尺寸程序化生成。
>
> **方向选定：结构规则模板**（方案三，见下方三方案对比）。

---

#### 十二.7.1 设计哲学

- MineColonies 式模板不适合：Lordling 的建筑大小由地契决定，用途由居民自行赋予
- 建筑只是物理外壳——功能性来自内部居民自行放置的功能方块
- 玩家感受：划地 → 几天后建筑工盖好了一栋有窗户有屋顶的房子
- **居民自主**：居民根据自己的需求（卧室、厨房等）、地契尺寸和经济能力，从模板库中选择合适的户型，自行建造

---

#### 十二.7.2 三方案对比

##### 方案一：成品蓝图

> 设计权在玩家/社区，居民是施工队。

玩家使用蓝图工具设计完整房间（门、卧室、厨房、花园、田地等），手动标注每个房间的功能作用，支持多步建造过程的模拟录制。录入后自动计算范围面积和建筑价值。居民地契范围足够时，从蓝图库中选择成品房建造。

| 优点 | 缺点 |
|------|------|
| 建筑美观可控 | 居民没有"选房子"的主体性，与"居民自主"理念冲突 |
| 实现难度适中 | 每栋房子都需要玩家亲手设计 |
| 社区可共享蓝图 | 批量生产同质化严重 |

##### 方案二：建筑结构（纯零件拼合）

> 设计权在算法，居民基于需求和人格自行拼合。

模仿现实建筑流程，从地基、承重柱、墙体、门、窗户、屋顶等做结构化拆分。玩家设计结构部件蓝图（如"3 格直墙"、"带窗墙"），居民建造时取用这些部件自行拼合。有懒惰特质的居民可能建得简陋，勤劳的建得精致——本身就是叙事。

| 优点 | 缺点 |
|------|------|
| 真正实现居民自主 | 工程难度最大 |
| 生成结果差异化（人格影响） | 拼合结果可能很丑，难以保证美观 |
| 部件可跨建筑复用 | 需要复杂的空间推理和合法性校验 |

##### 方案三：结构规则模板（选定方案）

> 设计权在模板设计者，选择权在居民。

**结构部件是居民的"词汇表"**（地基、墙、窗、屋顶等），但居民不自由拼合——他们从**结构规则模板库**中挑选，然后根据自己地契的尺寸和材料偏好微调参数。例如"三室一厅"模板在 7×7 地契和 10×10 地契上都能自适应。

**建造分层模型**：

| 层 | 驱动 | 说明 |
|----|------|------|
| **需求层** | 需求系统 | 我需要一间卧室、一个厨房——由功能区/需求系统驱动 |
| **选择层** | 地契尺寸 + 模板库 | 地契是 8×8，从模板库里挑适配的户型（"一室户"还是"两室一厅"） |
| **参数层** | 材料偏好 + 经济约束 | 模板中的"木板墙"→手头有石材就用石墙；材料不够→发委托采购 |
| **执行层** | 建筑工 AI | 逐块放置，过程中可能发生事件（下雨停工、材料短缺发委托） |

| 优点 | 缺点 |
|------|------|
| 居民有选择权（选什么户型、用什么材料） | 需要足够多的模板支撑多样性 |
| 美观可控（模板保证了结构合理性） | 玩家/社区需投入精力建设模板库 |
| 可适配任意地契尺寸 | 模板参数化有一定工程量 |
| 保留了人格差异化空间（材料偏好） | |

---

#### 十二.7.3 建造流程

```
居民获得地契（X×Y×Z 长方体）
    → 需求驱动：我需要卧室 + 厨房
    → 模板选择：根据尺寸和需求，从模板库筛选可用户型
    → 参数微调：适配实际尺寸、替换材料偏好
    → 生成材料清单 → 缺材料则向商店购买 / 向委托版发布需求委托
    → 建筑工逐方块放置
    → 完成 → 居民搬入 → 自行布置内部家具
```

---

#### 十二.7.4 结构零件定义（方案三的底层零件）

| 零件 | 放置规则 |
|------|---------|
| 地基 | 铺满底面，可选材质 |
| 承重柱 | 四角各一个，X/Z 跨度大时沿墙中线加柱 |
| 直墙 | 柱子之间填充，材质可由居民偏好替换 |
| 外转角墙 | 四角替换直墙（视觉更完整） |
| 门 | 一面墙上自动开一个（朝向道路或由模板指定） |
| 窗户 | 按模板规则分布 |
| 地板 | 铺满每层底面 |
| 屋顶边 | 四周向外凸出一格屋檐 |
| 屋顶角 | 四角收口（楼梯块或石板） |
| 斜屋顶 | 阶梯状向上收拢填充 |
| 栏杆 | 可选：有二楼/阳台时外沿生成 |

---

#### 十二.7.5 内部布置（居民自主）

建筑完工后，居民根据自身职业/需求自行放置内部功能方块：

- 床（每个居民一张）
- 箱子（储物）
- 职业相关工作台（熔炉/工作台/织布机等）
- 装饰物 [PLACEHOLDER]

玩家不需要操作——功能区自然生成。

---

#### 十二.7.6 模板的创建与发布

| 方式 | 说明 |
|------|------|
| **玩家自建 → 扫描录入** | 玩家手动建造一栋房子，使用蓝图工具扫描并标注功能分区（这是卧室/这是厨房），系统自动提取结构规则模板并参数化 |
| **社区共享** | 模板文件可分享，玩家导入到自己的模板库中 |
| **官方预设** | 模组内置少量基础模板（如"一室户"、"两室一厅"）作为兜底 |
