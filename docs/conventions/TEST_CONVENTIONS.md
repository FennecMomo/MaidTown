# 测试协作规范

## 工作流

```
开发者          AI
  │              │
  ├─ 请求测试 ──→│
  │              ├─ 生成 TEST_LOGGING.md（操作清单）
  │              ├─ 保留内部日志检查表（不写入文件）
  │              │
  ├─ 逐条测试 ──→│
  │  • 通过的报结果 │
  │  • 异常的报现象 │
  │  • 没测的不提   │
  │              │
  │←── 修复 ────│
  │              ├─ 修 bug
  │              ├─ 更新 TEST_LOGGING.md（移除已测项，标记状态）
  │              ├─ 记录 TEST_NOTES.md（通过/异常/待调整）
  │              │
  ├─ 继续测 ──→│  （循环）
  │              │
  │              │
```

## 规则

### 测试清单（`TEST_LOGGING.md`）
- AI 生成，给操作人看
- 每轮测试后 AI 更新：已通过的移除或标记 ✓，残留的保留
- □ 未测 / ✓ 通过 / ⚠ 有问题

### 测试笔记（`TEST_NOTES.md`）
- AI 维护，记录每轮结果
- 非 bug 的调整点（如"气泡延迟偏长"）记在这里，最后统一处理
- 真正的 bug 开独立的 `BUG-xxx.md`

### 操作人反馈
- 每次只报**实际测过的**条目
- 格式：`编号. 结果 + 备注`
- 没测到的不用说

### 问题清单同步（`TEST_LOGGING.md`）
- 操作人每次反馈的问题，AI 直接追加到 TEST_LOGGING.md 当前轮次下
- 同一功能点的问题合并为一条子项（如 #5-1），不同功能点开新条目（如 T1、N1）
- 代码修完标记“已修，待游戏验证”；只有操作人实际验证通过才标记 ✓。编译成功不等于游戏验证通过。

### AI 响应
- 根据操作人反馈查日志验证
- 修 bug → 重新打包 → 告知可继续测
- **每次收到反馈后立即更新 TEST_LOGGING.md 和 TEST_NOTES.md，不等操作人提醒**
- 调整清单，告知下一轮待测项
