## 它怎样实现生产自主

1. 玩家登记箱子、床、工作站，指定生产区域、库存订单及居民职业优先级。不是为每次搬运逐个点选执行者。`front/ui/screen/ResidentsPage.java` 可调整 `Keenness`，因此这个职业倾向首先是玩家配置，不能仅凭命名认为是居民内生志向。
2. `plugins/orders/Order.java` 保存目标容器、物品、库存低高水位、常驻开关和优先级。常驻订单低于低水位时要求补到高水位；这不是居民间带货币和产权的委托合同。
3. `core/engine/plan/Weaver.java` 将意图展开为工作依赖图，寻找背包、仓库或生产来源，再展开来源的原料需求和搬运。物料流与先后依赖分开，失去来源后可重新求供给。
4. `Planner.java` 处理开始、完成、失败、释放等消息，更新工作图并调用 `Tours.java` 排程。排程考虑前置工作、工位占用、背包、路径与时间范围；`Tours.Score` 先比较最后一位工人的完成时刻，再比较所有工人的完成时刻总和。这是生产效率导向的明确代码证据。
5. `plugins/BuiltinPlugins.java` 将人类、生产、建筑、农业、畜牧、渔业、巡逻、订单、铁路与发运注册为插件，可选接入 Sable 和 Modular Golems。可扩展职业能力与核心排程分离，值得借鉴。
6. 建筑使用图案／蓝图生成目标，再清理、供料及放置方块。README 列出的道路、桥、矿井、铁路等已有对应插件与资源；本次没有验证各图案的游戏效果。不要将建筑施工矿井直接等同于 MaidTown 的全部持续采矿、经济和产权设计。

## 居民的生活与个体差异

- `core/api/work/Urge.java` 支持权重及能否打断工作，`core/engine/labor/Urges.java` 在可用且未冷却的需求中选择最高权重。
- `plugins/person/living/LivingPresence.java` 提供吃饭和睡觉需求，区分紧迫与普通需求，`STOIC` 特长会影响普通需求是否打断工作；因此不能简单称其为完全没有个体差异的机器。
- `Rest.java` 按劳动时间及步行距离累积疲劳，睡眠恢复；`LivingNeed.java` 的移民生活条件为食物和床。这里的 Household 命名不足以证明婚姻家庭系统。
- `plugins/person/fear/FearPresence.java` 提供避险需求；`PersonBody.java` 为人类绑定 living、fear、patrol 参与项。
- `core/api/resident/body/BodyPerks.java` 按职业及全局经验升级并随机抽取特长；`GlobalPerks.java` 有负重、步速、节食等方向。已有劳动成长及需求差异，但不能由此推断社会人格、偏好关系或长期志向。
- 本次检索及上述入口未发现居民间好感关系、恋爱婚姻、亲属家庭、社会事件记忆或由这些经历影响后续选择的系统。此处是当前检查范围内的未发现，不是对未来扩展能力的否定，也不意味着玩家不可能从生产事故中自行感受到故事。

## 与 MaidTown 的关系

| 维度 | Folkways 本次证据 | MaidTown 现有设计与新确认 |
|---|---|---|
| 生产自主 | 目标库存、自动拆解工作、集中排程 | 真实生产、委托、搬运、施工重合度高 |
| 经济组织 | 所查订单与调度围绕殖民地供给 | 私产、居民出资经营、工资、交易、招标并非同一套机制；本次未找到对应完整经济系统 |
| 日常生活 | 吃饭、睡觉、疲劳、避险、成长 | 已有需求与作息方案，但此前社交故事仍留在长期章节 |
| 角色自主 | 所查倾向主要为工作优先级与生理需求 | 新确认强调自己的想法、社交、活动以及由此产生的故事 |
| 玩家身份 | 核心入口是殖民地配置与生产管理 | 用户明确玩家兼任领主与社会成员，可建立关系、组建家庭 |

结论：Folkways 已对生产自动化这一大片重叠问题提供实际代码，不能轻描淡写成“只是像”。但本次证据不足以支持“它已经完成 MaidTown 全部设计”，尤其不支持“它已实现用户原本的角色故事目标”。生产发生意外可以形成故事，然而可持续的角色故事还需要经历影响后续选择，而不仅是生产链自动恢复。

## 区块卸载专项核对（2026-10-11，同一提交）

用户在 Q39.3 要求先检查参考模组如何处理卸载。本次沿实体移除、居民名册、执行器、生活更新及设施检查路径核对，未运行游戏。结论限于该提交内置普通居民与生产路径，不推广到外部模组的独立区块加载或 Create 列车内部模拟。

- `core/engine/colony/Holdings.java:196` 的 `bodiesIn` 只返回已存在、未移除且 `isPositionEntityTicking` 的实体。`core/engine/labor/ColonyLabor.java:179` 只对这些实体调用 `runner.tick`，缺席者进入 `runners.away`，不是转入虚拟居民执行器。
- `core/engine/labor/BodyRunner.java:52` 设置 `AWAY_TICKS = 100`；`away`（224 起）在缺席达到该游戏 tick 时长后释放当前动作并通知调度器。20 TPS 下约 5 秒；不是玩家离开后继续工作 5 秒，缺席期间已不进入正常执行循环。
- `letGo`（197 起）释放工作节点；私人需求节点走取消。`clear`（611 起）清空当前节点及 windup 等运行中进度；`here`（216 起）重新通知居民到场。不能将这套逻辑说成所有动作都按中断进度恢复；已完成世界变化、订单记录与当前动作进度也不是同一回事。
- `plugins/person/ResidentEntity.java:185` 在移除时按原因处理；`core/api/colony/Release.java:25` 对区块卸载、随玩家卸载和跨维度返回空，由此仅退出当前在场集合，不按死亡／永久离开处理。`Holdings` 区分持久成员名册与不保存的 present 集合；实体自身也有常规保存／读取路径。
- `plugins/person/living/LivingPresence.java:110` 更新生活数值时通过 `level.getEntity` 查找居民，找不到 LivingEntity 就跳过；疲劳按实际劳动／步行回调积累。本次未见替代该路径的未加载居民生活推进器，不能将数据仍保存等同于后台继续生活。
- 库存、工作站及工作节点普遍检查 `isLoaded`／`hasChunkAt`：如 `core/engine/labor/Survey.java:249` 只读取加载的供给点、`plugins/wares/WaresPresence.java` 跳过未加载设施。未加载不等于仓库或居民从名册中删除，而是无法按正常现场路径使用。
- 搜索生产源码未见主动强制加载的常见 API（`forceChunk`、`setChunkForced`、`addRegionTicket`、`TicketController` 等）。仓库中有 forceload，但命中测试、基准和宣传场景脚本，例如 `tests/bench/large-colony.bench.ts:172` 强制加载测试城镇；不能据此宣称模组正常运行自动保活殖民地。

因此本次证据支持“保留成员与相关数据、依赖加载实体执行、缺席后释放工作并在返回时重新纳入调度”，而非“通过后台替身继续生产生活”。这部分没有解决 MaidTown 已提出的卸载后持续居民模拟需求；也不能仅凭源码判断百人城镇性能。

## 对后续讨论的建议（未确认）

- 先定义一个希望自然发生且玩家能参与的角色故事，检查“个人动机—行为—他人反应—留下经历—改变后续选择”是否成立，再决定需要多少生产与经济细节。不是先追求全产业链完成。
- 既有工作能力可作为角色行动基础；关系、记忆、个人目标是否影响劳动选择必须另作设计，不能仅给效率系统增加名字、闲聊或事件文本就认为目标已达成。
- 地皮算式、复杂招标和全链条价格细节可建议延后，但未获用户确认前不删除现有规则；私产与经营也可能承载家庭、利益和矛盾，不能全部视为无用。
- 是否依赖 Folkways、仅借鉴结构或完全独立尚未讨论。其公开插件 API 不等于现成 TLM 兼容层；没有本次证据证明能直接接入。技术栈、居民载体、加载策略、产权语义均需单独验证。
